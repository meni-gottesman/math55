1.1How a Java program is put together

Big idea

Java is statically typed: every variable and expression has a type the compiler knows before the program runs. Most mistakes are caught by the compiler (a compile error, nothing runs); the rest blow up while running (a runtime error, i.e. an exception). Exam questions constantly ask which of the two you get.

Plain definitions

  • Class: a blueprint. All Java code lives inside some class. A file Dog.java holds a class Dog.
  • main: public static void main(String[] args) is where execution starts when you run a class.
  • Object / instance: a thing built from the blueprint with new. Each has its own copy of the instance variables.
  • Constructor: the special method (same name as the class, no return type) that runs when you say new Dog(5).
  • Compile → run: javac checks types and makes bytecode; java runs it. (java File.java does both in one step.)
public class Dog {
    public int weight;               // instance variable
    public Dog(int w) { weight = w; } // constructor
    public void bark() {             // instance method
        if (weight < 10) System.out.println("yip");
        else System.out.println("woof");
    }
    public static void main(String[] args) {
        Dog d = new Dog(51);
        d.bark();                    // prints woof
    }
}

Small facts that show up in “what does this print”

  • Integer division truncates toward zero: 7 / 2 is 3, -7 / 2 is -3, and -7 % 3 is -1 (the remainder takes the sign of the left side). 7 / 2.0 is 3.5.
  • char is a number: 'a' + 1 is the int 98; (char) ('a' + 1) is b.
  • String + is left to right: 1 + 2 + "3" + 4 + 5 is "3345". The first + adds ints; once a String appears, everything after is concatenation.
Trap

Type errors are compile errors, even on lines that would never run. int x = "hi"; anywhere in the file means nothing runs at all.

What does System.out.println(7 / 2 + " " + (-7 % 3) + " " + ('a' + 1)); print?tap

3 -1 98. Integer division drops the .5; the remainder keeps the sign of −7; adding a char and an int gives an int.

1.2Static vs instance

Big idea

Instance things belong to one object. Static things belong to the class itself, so there is exactly one copy shared by every object.

Variableone per object (d.weight)one total (Dog.binomen)
Methodneeds an object; can use thisno object; no this; can’t touch instance variables directly
Call asd.bark()Dog.maxDog(a, b)

Why have static at all? Some facts are about the species, not the dog (the scientific name), and some functions don’t need any particular object (Math.max, maxDog(a, b)).

Example · one shared copy 
public class Dog {
    public int weight; public String name;
    public static String binomen;
    public Dog(int w) { weight = w; }
    public static Dog maxDog(Dog a, Dog b) {
        return a.weight > b.weight ? a : b;
    }
}
Dog d1 = new Dog(5), d2 = new Dog(30);
d1.name = "Fido";
Dog.binomen = "Canis";
d2.binomen = "Lupus";   // legal but misleading
System.out.println(d1.binomen + " " + Dog.binomen
    + " " + d1.name + " " + d2.name);
System.out.println(Dog.maxDog(d1, d2).weight);
  1. d2.binomen = "Lupus" writes the single static variable, even though it’s spelled through d2.
  2. So both d1.binomen and Dog.binomen read Lupus.
  3. d2.name was never assigned: object fields default to null (ints to 0, booleans to false).
  4. Output: Lupus Lupus Fido null, then 30.
Trap

Inside a static method, writing weight (an instance variable) is a compile error: “non-static variable cannot be referenced from a static context”. There is no this to ask.

1.3Primitives, references & the Golden Rule of Equals

Big idea

A variable is a box holding bits. y = x copies the bits in box x into box y. That is the whole rule. What changes is what the bits mean: for a primitive they are the value; for everything else they are an address (an arrow to an object).

Golden Rule of Equals (GRoE): y = x copies the bits.For primitives you get an independent copy of the value. For reference types you get a copy of the arrow, so both variables point at the same object.

Plain definitions

  • Primitive types (8 of them): byte short int long float double boolean char. The box holds the value itself.
  • Reference types: everything else, including arrays, Strings and every class. The box holds an address (64 bits) or null.
  • new builds an object somewhere in memory and returns its address. That address is what gets stored.
  • Parameter passing is also GRoE (“pass by value”): calling f(x) copies x’s bits into f’s parameter.
Example · same code, two kinds of box 
int x = 5; int y = x; y = 10;
System.out.println(x + " " + y);          // 5 10

Walrus a = new Walrus(1000);
Walrus b = a;          // copy the arrow
b.weight = 5;          // follow arrow, change object
System.out.println(a.weight + " " + b.weight); // 5 5
  1. y = x copies the bits for 5; changing y later can’t touch x.
  2. b = a copies an address. Now two arrows lead to one walrus.
  3. b.weight = 5 means “follow b’s arrow and change that object”. a sees it because it’s the same object.
Example · passing to a method 
static void bump(int k, int[] arr) {
    k = k + 1;          // changes the local copy only
    arr[0] = arr[0] + 1; // follows the copied arrow
}
static void reassign(Walrus w) {
    w = new Walrus(99); // local w now points elsewhere
    w.weight = 100;
}
int n = 3; int[] arr = {3};
bump(n, arr);
System.out.println(n + " " + arr[0]);   // 3 4
Walrus w = new Walrus(7); reassign(w);
System.out.println(w.weight);           // 7
  1. k got a copy of 3; incrementing it is invisible outside.
  2. arr got a copy of the arrow, so arr[0] += 1 changes the caller’s array: 4.
  3. In reassign, w = new … re-aims only the local arrow. The caller’s walrus still weighs 7.
Trap

“Java passes objects by reference” is the wrong mental model. Java passes everything by value; for objects the value happens to be an arrow. A method can mutate the caller’s object but can never make the caller’s variable point somewhere else.

After int[] p = {1, 2, 3}; int[] q = p; q = new int[]{7, 8}; q[0] = 0;, what are p[0] and q[0]?tap

p[0] is 1, q[0] is 0. q = p briefly shared the array, but q = new int[]{7, 8} re-aimed q at a brand-new array before anything was changed. Only the new array’s first slot becomes 0.

1.4Box-and-pointer diagrams & arrays

Big idea

Draw every variable as a box. Primitives are written inside the box; references are drawn as an arrow to an object (or a slash for null). If you draw honestly, every aliasing puzzle answers itself.

Arrays

  • An array is an object: a fixed number of numbered boxes, all the same type, plus a length (a field, no parentheses).
  • Three ways to make one: new int[3] (all zeros), new int[]{1, 2, 3}, int[] a = {1, 2, 3} (only in a declaration).
  • The size is fixed forever. Indexing outside 0 … length−1 throws ArrayIndexOutOfBoundsException at runtime.
  • An array of objects (new Dog[3]) is an array of arrows, all null at first; no dogs are built.
  • A 2D array is an array of arrows to arrays. The rows can have different lengths and can even be shared.
Example · a 2D array with a shared row 
int[][] m = new int[3][];   // 3 null arrows
m[0] = new int[]{1};
m[1] = new int[]{2, 3};
m[2] = m[1];                // copy the arrow
m[2][0] = 9;
System.out.println(m[1][0] + " " + (m[1] == m[2])
    + " " + m.length);      // 9 true 3
m ──► [ • | • | • ]
        │   │   └──────┐
        ▼   ▼          │
      [1] [ 9 | 3 ] ◄──┘
  1. new int[3][] builds the outer array with three null arrows (the rows don’t exist yet).
  2. m[2] = m[1] copies the arrow (GRoE), so rows 1 and 2 are the same array.
  3. Writing through m[2] is writing to row 1. == on references compares addresses, so it’s true.

How to draw a diagram from code

  1. For each declaration, draw a labeled box. Primitive: write the value. Reference: leave room for an arrow.
  2. For each new, draw the object (with its own field boxes) and an arrow from wherever the address is stored.
  3. For each assignment, copy exactly what’s in the right-hand box: a number, or an arrow to the same place.
  4. Objects nothing points to are garbage; cross them out (they can never be reached again).
Trap

a == b on arrays or objects asks “same address?”, never “same contents?”. Two separate arrays {1, 2} and {1, 2} are !=. For contents use Arrays.equals or a class’s equals.

String[] s = new String[2]; System.out.println(s[0]);. What prints, and what would s[0].length() do?tap

It prints null: an array of references starts out full of null. s[0].length() compiles fine but throws a NullPointerException at runtime, because there is no object to follow the arrow to.

1.5Recursion

Big idea

A recursive method solves a problem by trusting itself on a smaller version of the same problem. Two parts are always needed: a base case you can answer directly, and a recursive case that makes progress toward it.

Why it works: the leap of faith

Don’t trace every call in your head. Assume the recursive call returns the right answer for the smaller input, and check that you correctly build the full answer from it. If the base case is right and every call shrinks the input, induction guarantees the whole thing is right.

What the computer actually does

Each call gets its own frame on the call stack with its own copies of the parameters and locals. A call waits until the calls it made return. Too-deep recursion (or a missing base case) gives a StackOverflowError.

Example · tracing a tree of calls 
static int f(int n) {
    if (n <= 1) return 1;
    return f(n - 1) + f(n - 2);
}
System.out.println(f(4));
  1. f(1) and f(0) are base cases: 1 each.
  2. f(2) = f(1) + f(0) = 2.
  3. f(3) = f(2) + f(1) = 3.
  4. f(4) = f(3) + f(2) = 5. Prints 5. (Notice f(2) gets computed twice; this recursion makes exponentially many calls, a preview of B5.)
Trap

A base case that the input can skip over is as bad as none. if (n == 0) return …; return g(n - 2); recurses forever on odd n. Use <= or check every path reaches the base.

Write a recursive static int sum(int[] a, int i) returning a[i] + a[i+1] + … + a[a.length−1].tap 
static int sum(int[] a, int i) {
    if (i >= a.length) return 0;   // nothing left
    return a[i] + sum(a, i + 1);   // trust the rest
}

Base case: an empty suffix sums to 0. Recursive case: first element plus the (trusted) sum of the rest. Call it as sum(a, 0). The helper parameter i is the standard trick for recursing over an array without copying it.

1.6IntLists: a list made of arrows

Big idea

An array can’t grow. A linked list can: each node holds one item and an arrow to the rest of the list. The rest of a list is itself a list, so list methods are naturally recursive.

public class IntList {
    public int first;
    public IntList rest;
    public IntList(int f, IntList r) { first = f; rest = r; }
}
IntList L = new IntList(5, null);
L = new IntList(10, L);
L = new IntList(15, L);     // 15 -> 10 -> 5
L ──► [15| •]──► [10| •]──► [5| / ]

Each new node is built in front, with rest pointing at the old list. The last node’s rest is null.

Recursive vs iterative size

public int size() {              // recursive
    if (rest == null) return 1;
    return 1 + rest.size();
}
public int iterativeSize() {     // walk a pointer
    IntList p = this; int total = 0;
    while (p != null) { total += 1; p = p.rest; }
    return total;
}
public int get(int i) {          // Θ(i) time
    if (i == 0) return first;
    return rest.get(i - 1);
}

Non-destructive vs destructive

A non-destructive method builds new nodes and leaves the input alone. A destructive one changes the existing nodes. Exams love asking what the original list looks like afterward.

Example · incrList vs dincrList on L = [15 10 5] 
static IntList incrList(IntList L, int x) {
    if (L == null) return null;
    return new IntList(L.first + x, incrList(L.rest, x));
}
static IntList dincrList(IntList L, int x) {
    if (L == null) return null;
    L.first += x; dincrList(L.rest, x); return L;
}
IntList M = incrList(L, 2);  // L: [15 10 5]  M: [17 12 7]
IntList N = dincrList(L, 1); // L: [16 11 6]  N == L
  1. incrList calls new once per node, so M is a completely separate chain. L is untouched.
  2. dincrList never calls new; it edits L’s nodes in place and returns the same arrow. So afterward L is [16 11 6] and N == L is true.
Example · an aliasing puzzle (draw it!) 
IntList A = new IntList(1, new IntList(2,
                new IntList(3, null)));
IntList B = A.rest;
B.first = 20;
A.rest.rest = A;
System.out.println(A.first + " " + A.rest.first + " "
    + A.rest.rest.first + " " + B.rest.first);
  1. B points at the second node. B.first = 20 changes that node: A is now 1 → 20 → 3.
  2. A.rest.rest = A: the second node’s rest now points back at the first node. The 3 node is garbage; the list is a cycle 1 → 20 → 1 → 20 → …
  3. A.rest.rest.first is the first node again: 1. B.rest is also the first node: 1.
  4. Output: 1 20 1 1.
Trap

In a destructive method, save p.rest before you overwrite it. Reversing a list in place needs three pointers (prev, p, next), or you lose the rest of the list.

Trace this in-place reverse on R = [1 2 3]. What do reverse(R) and then R print?tap 
static IntList reverse(IntList p) {
    IntList prev = null;
    while (p != null) {
        IntList next = p.rest;
        p.rest = prev; prev = p; p = next;
    }
    return prev;
}

[3 2 1] then [1]. Each pass flips one arrow backward. R still points at the node holding 1, which is now the last node (its rest is null), so printing R shows just [1]. To keep the reversed list you must write R = reverse(R);.

Why is L.get(i) Θ(i) for an IntList but Θ(1) for an array?tap

An array’s slots sit side by side in memory, so the address of slot i is computed directly (start + i × size). A linked list has no such layout: the only way to find node i is to follow i arrows from the front.

Two ways to build a list that grows: chains of nodes (fast at the ends) and resizing arrays (fast everywhere by index). Plus how to know your code works.

2.1Testing

Big idea

A test is code that runs your code on an input whose correct answer you already know, and complains if the answer differs. Tests turn “I think it works” into “it works on these cases”, and they catch you when a later change breaks something.

Plain definitions

  • Unit test: checks one small method in isolation. Integration test: checks that pieces work together.
  • Assertion: a line that fails the test if a condition is false. 61B uses JUnit with the Truth library: assertThat(actual).isEqualTo(expected);, assertThat(list).containsExactly(1, 2, 3).inOrder();, assertThat(b).isTrue();.
  • A method marked @Test is run by the test runner; each one passes or fails independently.
  • Test-driven development: write the test first, watch it fail, then write code until it passes.
  • Randomized / comparison testing: run your implementation and a trusted one on the same random operations and check they always agree.
@Test
public void addFirstThenGet() {
    SLList L = new SLList();
    L.addFirst(10);
    L.addFirst(5);
    assertThat(L.get(0)).isEqualTo(5);
    assertThat(L.size()).isEqualTo(2);
}

What makes a good test suite

  • Edge cases: empty structure, one element, removing the last element, then adding again; resizing boundaries (exactly full, one past full).
  • Check state after a sequence of mixed operations, not just one call.
  • Tests should be small and specific, so a failure points at the bug.
Trap

Passing tests prove correctness only on the cases tested. A suite that never empties a deque and refills it won’t catch a broken sentinel. Also: isEqualTo uses .equals; checking two arrays with it compares addresses unless you use the array-aware assertion.

A deque passes tests for addFirst, addLast and removeFirst separately but crashes in use. Name two sequences you should have tested.tap

(1) Add one item, remove it, then add again (the empty → nonempty → empty → nonempty transition, where front/back pointers usually go wrong). (2) Add enough to force a resize, then remove from both ends and check order. More generally: interleave operations, and compare against a trusted ArrayDeque/LinkedList on random sequences.

2.2SLList and the sentinel node

Big idea

Raw IntLists make the user juggle nodes. An SLList wraps the chain in a class that hides the nodes, keeps a cached size, and uses a permanent dummy node, the sentinel, so that the empty list is no longer a special case.

The pieces

  • Nested class IntNode inside SLList. Marked private static: private because users shouldn’t see it; static because a node never needs to look at its enclosing SLList (saves a hidden pointer per node).
  • Cached size: update a size field on every add/remove so size() is Θ(1) instead of walking the list.
  • Sentinel: a node that’s always there, holding a junk item. The real first item is sentinel.next.
  • Invariant: a fact that is always true between operations. Here: “sentinel is never null; the first real item, if any, is at sentinel.next; size equals the number of real nodes.”
public class SLList {
    private static class IntNode {
        int item; IntNode next;
        IntNode(int i, IntNode n) { item = i; next = n; }
    }
    private IntNode sentinel = new IntNode(-999, null);
    private int size = 0;
    public void addFirst(int x) {
        sentinel.next = new IntNode(x, sentinel.next);
        size += 1;
    }
    public void addLast(int x) {
        IntNode p = sentinel;          // never null!
        while (p.next != null) p = p.next;
        p.next = new IntNode(x, null);
        size += 1;
    }
}

Why the sentinel works

Without it, addLast on an empty list must check “is first null?” before walking, because there is no node to start from. With a sentinel there is always a node to start from, so one loop handles every case. Fewer special cases means fewer bugs.

Example · addFirst(10), addLast(20), addFirst(5) 
start:        S ─► /
addFirst(10): S ─► 10 ─► /
addLast(20):  S ─► 10 ─► 20 ─► /
addFirst(5):  S ─► 5 ─► 10 ─► 20 ─► /     size 3

Generics

To hold any type, write SLList<T> and use T for the item type. Users write SLList<String>. Generic type arguments must be reference types, so a list of ints is SLList<Integer>; Java converts between int and Integer automatically (autoboxing).

SLList opTimeWhy

Trap

Adding a last pointer makes addLast fast but not removeLast: after removing the last node you must set last to the second-to-last node, and a singly linked list can only find it by walking from the front. That’s the motivation for DLLists.

2.3DLList and the circular sentinel

Big idea

Give each node a prev arrow as well as next. Then from any node you can step either way, so both ends become Θ(1). Best design: one sentinel whose next is the first item and whose prev is the last item, so the list is a circle.

empty:   S.next = S, S.prev = S

[5, 10]: ┌──────────────────────────┐
         ▼                          │
         S ⇄ (5) ⇄ (10) ⇄ back to S ┘
         S.next = 5, S.prev = 10
public void addLast(T x) {
    Node last = sentinel.prev;
    Node n = new Node(last, x, sentinel); // prev, item, next
    last.next = n;
    sentinel.prev = n;
    size += 1;
}
public T removeFirst() {
    if (size == 0) return null;
    Node first = sentinel.next;
    sentinel.next = first.next;
    first.next.prev = sentinel;
    size -= 1;
    return first.item;
}

Why circular?

Alternatives exist (two sentinels, front and back), but with one circular sentinel the “last” node is just sentinel.prev, the empty list is a sentinel pointing at itself, and no operation ever meets null. Every add and remove rewires exactly 4 arrows (2 for the new node, 2 on its neighbours).

OpDLList
add/remove/get at either endΘ(1)
get(i)Θ(i) (could walk from the nearer end: still Θ(n) worst)
sizeΘ(1) cached
Trap

When removing, update both neighbours: sentinel.next and first.next.prev. Forgetting the prev side leaves a list that looks right going forward and wrong going backward, which shows up only when you later removeLast.

In a circular-sentinel DLList with exactly one item x, what are sentinel.next, sentinel.prev, x.next and x.prev?tap

sentinel.next = x, sentinel.prev = x, x.next = sentinel, x.prev = sentinel. A circle of two nodes. Removing x must restore sentinel.next = sentinel.prev = sentinel.

2.4AList: resizing arrays & amortized Θ(1)

Big idea

Linked lists are slow at get(i). An array list stores items in an array (instant indexing) and, when the array fills up, copies everything into a bigger array. The key design question is how much bigger. Answer: multiply the size (e.g. ×2), never add a constant.

public class AList<T> {
    private T[] items = (T[]) new Object[8];
    private int size = 0;          // next free slot
    public void addLast(T x) {
        if (size == items.length) resize(size * 2);
        items[size] = x;
        size += 1;
    }
    private void resize(int cap) {
        T[] a = (T[]) new Object[cap];
        System.arraycopy(items, 0, a, 0, size);
        items = a;
    }
    public T get(int i) { return items[i]; }
    public T removeLast() {
        T x = items[size - 1];
        items[size - 1] = null;    // let it be garbage collected
        size -= 1;
        return x;
    }
}

Invariants

  • The next item goes in items[size]. The last item is items[size − 1]. The number of items is size.
  • Generic arrays can’t be created directly: new T[8] is a compile error, so we create Object[] and cast (a warning, not an error).

Why multiplicative resizing gives amortized Θ(1)

Count the total number of item copies to do n addLasts starting from capacity 1.

  • Grow by +1 every time full: resizes copy 1, 2, 3, …, n−1 items, total n(n−1)/2 ∈ Θ(n²). That’s Θ(n) per add on average. For n = 1000: 499,500 copies.
  • Double when full: resizes happen at sizes 1, 2, 4, …, 512 and copy that many items, total 1 + 2 + 4 + ⋯ + 512 = 1023. Generally less than 2n, so Θ(n) total and Θ(1) per add on average.
1 + 2 + 4 + ⋯ + 2k = 2k+1 − 1 < 2 · (largest term)A geometric sum is dominated by its last term. That’s the whole reason doubling works: the one expensive resize is paid for by the cheap adds since the previous resize.

Amortized cost means: total cost of a sequence of operations divided by the number of operations, in the worst case over sequences. A single add can still cost Θ(n) (the one that triggers a resize); it’s the average over the sequence that is Θ(1). Any constant factor > 1 (×1.5, ×3) works; only the constant changes.

Shrinking

To save memory, halve the array when it becomes mostly empty. Halve when usage drops to ¼, not ½. If you halved at ½ full, a user alternating add/remove right at the boundary would trigger a Θ(n) resize on every single operation.

OpAListDLList
get(i)Θ(1)Θ(n)
addLastΘ(1) amortized (Θ(n) worst single)Θ(1)
removeLastΘ(1) (amortized with shrinking)Θ(1)
addFirstΘ(n) (shift everything) unless circularΘ(1)
Trap

“addLast is Θ(1)” is wrong if the question asks about a single worst-case call: that one can be Θ(n). Read whether the question says amortized/average over many operations or the worst case for one call. And if the resize policy is “add 100 slots”, the amortized cost is Θ(n), not Θ(1).

An AList starts at capacity 1 and grows by ×3 when full. How many item copies happen during 100 addLasts?tap

Resizes happen when size hits 1, 3, 9, 27, 81 (the next, 243, is never reached). Copies: 1 + 3 + 9 + 27 + 81 = 121. That’s about 1.2 copies per add: still Θ(1) amortized, just a different constant.

2.5Circular arrays (array deques)

Big idea

An AList is slow at the front because adding there shifts everything. Fix: let the items wrap around. Keep an index front of the first item; the array is treated as a circle, so stepping left from index 0 lands on the last index.

item i lives at (front + i) mod capacityaddFirst: front = floorMod(front − 1, cap), then write there. addLast: write at (front + size) % cap. Both Θ(1) apart from resizing.

Unit B3 · Inheritance & dynamic dispatch

The rules that decide which method actually runs. These are the most mechanical points on any 61B exam once you know the two-step procedure.

3.1Interfaces

Big idea

An interface is a promise: “anything of this type can do these methods.” Code written against the interface works with every class that keeps the promise. This is how one max function or one test can handle an AList and a DLList alike.

Plain definitions

  • interface List61B<T> { void addLast(T x); T get(int i); int size(); } lists method signatures (the what).
  • class AList<T> implements List61B<T> must supply bodies for all of them (the how). Missing one is a compile error.
  • is-a: an AList is a List61B, so List61B<String> L = new AList<>(); is legal. A List61B variable can hold any implementing class.
  • @Override on an implementing method asks the compiler to check you really are overriding something (catches typos).
  • Default methods: an interface may give a method a body using default, written only in terms of the other interface methods. Implementers inherit it and may override it.
  • You can’t new an interface. Interfaces have no instance variables (only public static final constants).
interface Lst {
    int size(); int get(int i);
    default void print() {         // works for any Lst
        for (int i = 0; i < size(); i++)
            System.out.print(get(i) + " ");
        System.out.println();
    }
}
class Arr implements Lst {
    public int size() { return 3; }
    public int get(int i) { return i * i; }
    @Override public void print() { System.out.println("Arr print"); }
}
Lst l = new Arr();
l.print();                          // Arr print

The override wins even though the variable’s type is Lst: which body runs depends on the object, not the variable. Section 3.3 makes this precise.

Trap

Methods implementing an interface must be public (interface methods are implicitly public); leaving off public is a compile error (“attempting to assign weaker access privileges”).

3.2Implementation inheritance: extends

Big idea

class B extends A makes B a subclass of A: B automatically gets all of A’s instance and static variables and methods (other than constructors), may override methods, and may add new ones. Use it for genuine is-a relationships.

  • Constructors are not inherited, but every constructor of B must start by running a constructor of A. If you don’t write super(…) as the first line, Java inserts super() (no arguments) for you. If A has no no-argument constructor, that’s a compile error.
  • super.method() calls A’s version from inside B (handy for “do what the parent does, plus a bit more”).
  • B inherits A’s private members but can’t touch them by name.
  • Every class implicitly extends Object, which supplies equals, hashCode, toString.
Example · constructor chaining 
class Animal { Animal() { System.out.println("Animal()"); } }
class Dog extends Animal { Dog() { System.out.println("Dog()"); } }
class Puppy extends Dog {
    Puppy() { super(); System.out.println("Puppy()"); }
}
new Puppy();
  1. Puppy’s constructor first calls Dog’s, which (implicitly) first calls Animal’s.
  2. Output top-down: Animal(), Dog(), Puppy(). The parent part of an object is always built first.

Is-a vs has-a

A Stack has a list inside it (composition: a field). It is not a list, because a list allows get(i) and a stack shouldn’t. Inheriting when you mean has-a exposes methods that break your invariants. Inheritance also couples you to the parent’s internals: if a parent’s method calls another overridable method, overriding one can unexpectedly change the other.

Trap

Writing a method in B with the same name but different parameter types does not override A’s; it adds an overload. With @Override the compiler catches it; without, it silently does the wrong thing (see the equals(Pt) trap in 4.2).

3.3Static type vs dynamic type

Big idea

Every variable has two types. The static type is what it’s declared as; it never changes and it’s all the compiler knows. The dynamic type is the class of the object it currently points to, decided at runtime by whatever new built it.

Animal a = new Dog();
// static type of a: Animal   (from the declaration)
// dynamic type of a: Dog     (from the object)

Rule 1 · the compiler only looks at static types

  • Assignments: X v = expr compiles only if expr’s static type is X or a subtype of X. So Dog d = a; fails (a is “just an Animal” as far as the compiler knows) even though it really holds a Dog.
  • Method calls: a.method() compiles only if the static type (or its ancestors) has a method by that name accepting those argument types. If only Dog has fetch(), then a.fetch() is a compile error.

Rule 2 · at runtime, overridden methods use the dynamic type

When the program runs a.speak() and Dog overrides speak, Dog’s version runs. This is dynamic method selection.

Exceptions to Rule 2 (no dynamic selection)

  • Static methods: chosen by static type. A static method with the same signature in a subclass hides rather than overrides.
  • Fields: chosen by static type. A field in B with the same name as one in A hides it; a.name reads A’s field.
Example · fields and static methods follow the static type 
class Animal { String name = "animal";
    static void sniff() { System.out.println("Animal sniff"); } }
class Dog extends Animal { String name = "dog";
    static void sniff() { System.out.println("Dog sniff"); } }
Animal a = new Dog(); Dog d = new Dog();

    + ((Animal) d).name);                     // animal dog animal

3.4Overloading vs overriding: the two-step rule

Big idea

Overloading = same name, different parameter types, chosen by the compiler using static types. Overriding = a subclass method with the exact same signature, chosen at runtime using the object’s dynamic type. A call goes through both steps in that order.

The procedure for x.m(arg)

  1. Compile time. Look in the static type of x (and its ancestors) for methods named m. Pick the one whose parameter type best matches the static type of arg (the most specific that fits). If none fits: compile error. The compiler now locks in that exact signature, say m(Animal).
  2. Run time. Look at the dynamic type of x. If it overrides that exact signature m(Animal), run the override; otherwise run the inherited one. The dynamic type of arg is never consulted.
Example · the classic puzzle 
class A {
    void f(A x) { System.out.println("A.f(A)"); }
    void g() { f(this); }

    void f(A x) { System.out.println("B.f(A)"); }
    void f(B x) { System.out.println("B.f(B)"); }

  2. b.f(b): static type B has f(A) and f(B); argument static type B, the most specific match is f(B) → B.f(B).
  3. b.f(a): argument’s static type is A, so only f(A) fits → lock in f(A) → runtime B → B.f(A). (Even though a really holds a B.)
  4. b.g(): g is inherited from A. Inside A’s body, this has static type A, so f(this) locks in f(A); at runtime this is a B → B.f(A).
  5. ((A) b).f(b): the cast changes the static type to A → only f(A) → runtime B → B.f(A).

3.5Casting: compile errors vs runtime errors

Big idea

A cast (Dog) a tells the compiler “trust me, treat this as a Dog”. It changes the static type of that one expression and nothing else. It doesn’t change the object. At runtime Java checks the promise; if the object isn’t really a Dog (or subclass), you get a ClassCastException.

Decision procedure for a cast (T) expr

  2. Run time: is the object’s dynamic type T or a subtype of T? If not: ClassCastException.

3.6Higher-order functions

Big idea

A higher-order function takes a function as input or returns one. Java has no bare function values, so you pass an object whose class implements a one-method interface. A lambda is shorthand that makes such an object for you.

The three protocols that let your own classes plug into Java’s for-each loops, hash sets and sorting.

4.1Iterators and Iterable

Big idea

The enhanced for loop for (T x : thing) works on anything that can hand out an iterator: an object that remembers a position and can answer “is there more?” and “give me the next one”.

  • Iterable<T>: one method, Iterator<T> iterator(). Your collection implements this.
  • Iterator<T>: boolean hasNext() and T next(). Usually a private inner (non-static) class, so it can see the collection’s fields.
  • The for-each loop is just shorthand for:
Iterator<T> it = thing.iterator();
while (it.hasNext()) {
    T x = it.next();
    ...
}
Example · an Iterable of even numbers below n 
class EvenRange implements Iterable<Integer> {
    int n;
    EvenRange(int n) { this.n = n; }
    public Iterator<Integer> iterator() { return new It(); }
    private class It implements Iterator<Integer> {
        int cur = 0;                      // the remembered position
        public boolean hasNext() { return cur < n; }
        public Integer next() { int r = cur; cur += 2; return r; }
    }
}
for (int x : new EvenRange(7)) System.out.print(x + " ");
// 0 2 4 6
Iterator<Integer> it = new EvenRange(4).iterator();
System.out.println(it.next() + " " + it.hasNext() + " "
    + it.next() + " " + it.hasNext());   // 0 true 2 false
  1. Each call to iterator() makes a fresh It with cur = 0, so two loops over the same range don’t interfere.
  2. hasNext must not change state; next returns the current item and advances.
Trap

(1) A class that implements Iterator but not Iterable can’t go in a for-each loop. (2) Modifying a Java collection while for-each-ing over it (e.g. list.remove inside the loop) typically throws ConcurrentModificationException. (3) Store the iterator’s position in the iterator, not the collection, or two simultaneous iterations break each other.

4.2==, equals and the hashCode contract

Big idea

== compares the bits in the boxes: values for primitives, addresses for references. .equals is a method that asks “do these represent the same thing?”. Object’s default equals is just ==; you override it to compare contents. If you override equals, you must override hashCode to match.

Example · predict the output

    + " " + i3.equals(i4));
  1. Two new Strings: different objects, same characters → false true.
  2. Autoboxing reuses cached Integer objects for −128…127, so i1 == i2 is true by accident; 128 isn’t cached, so i3 == i4 compares two different objects → true false true.
  3. Moral: never use == on objects when you mean equality.

Writing equals properly

@Override
public boolean equals(Object o) {        // must take Object!
    if (this == o) return true;          // fast path
    if (!(o instanceof Pt other)) return false; // null or wrong type
    return x == other.x && y == other.y;
}
@Override
public int hashCode() { return 31 * x + y; }

Rules equals must follow: reflexive (x.equals(x)), symmetric, transitive, consistent (same answer if nothing changed), and x.equals(null) is false (no exception).

The contract: a.equals(b) ⟹ a.hashCode() == b.hashCode()Equal objects must have equal hash codes. The converse need not hold (different objects may collide). Hash-based collections (HashSet, HashMap) look in the bucket chosen by hashCode first, and only then call equals.

Why it matters: if you override equals but not hashCode, two equal Pts get (almost surely) different default hash codes, land in different buckets, and set.contains(new Pt(1, 2)) says false right after you added an equal Pt. Unit B11 builds the hash table that makes this concrete.

Unit B5 · Asymptotics

How to say “how fast” without a stopwatch: count work as a function of the input size, then keep only the shape of the growth.

5.1Θ, O and Ω

Big idea

Timing code on a laptop tells you about that laptop. Instead we count how many basic steps the code does as a function of the input size N, and then ignore everything except how that count grows as N gets large. Doubling N doubles a Θ(N) count but quadruples a Θ(N²) count. That difference survives every hardware upgrade.

Plain definitions

R(N) ∈ Θ(f(N)) ⇔ k₁·f(N) ≤ R(N) ≤ k₂·f(N)for some positive constants k₁, k₂ and every N past some point. “R grows exactly like f, up to constant factors.”
R(N) ∈ O(f(N)) ⇔ R(N) ≤ k₂·f(N)Upper bound only: “R grows no faster than f.”
R(N) ∈ Ω(f(N)) ⇔ R(N) ≥ k₁·f(N)Lower bound only: “R grows at least as fast as f.” Θ means both O and Ω at once.

How to simplify a count

  1. Write (or estimate) the number of steps, e.g. 3N² + 10N log N + 500.
  2. Keep only the fastest-growing term: 3N².
  3. Drop its constant: Θ(N²).

Why it’s legal: for large N the biggest term swamps the others (at N = 10⁶, N² is 10¹² while 10N log N is about 2·10⁸), and constants are exactly what Θ is allowed to ignore.

The growth ladder

1 ≺ log N ≺ √N ≺ N ≺ N log N ≺ N² ≺ N³ ≺ 2ᴺ ≺ N! ≺ NᴺEach one eventually beats every constant multiple of the ones to its left. Log base doesn’t matter: log₂N and log₁₀N differ by a constant factor, so Θ(log N) covers both.
Trap

O is not “worst case” and Θ is not “average case.” They are statements about a function. You can give the worst-case runtime a Θ bound (“worst case is Θ(N²)”) and the best-case runtime a different Θ bound. Also, O is only an upper bound: a linear-time method is technically O(N²) too. On exams, give the tightest bound unless told otherwise.

Is 5N² + N log N in Θ(N²)? In O(N³)? In Ω(N³)?tap

Θ(N²): yes. N² is the dominant term. O(N³): yes, since anything Θ(N²) grows no faster than N³ (a loose but true bound). Ω(N³): no, N² eventually falls below every constant times N³.

Simplify: Θ(log(N²)), Θ(log²N), Θ(2^(N+1)), Θ(4ᴺ) vs Θ(2ᴺ).tap

log(N²) = 2 log N, so Θ(log N). log²N = (log N)² stays Θ(log²N); it’s genuinely bigger. 2^(N+1) = 2·2ᴺ, so Θ(2ᴺ). But 4ᴺ = 2ᴺ·2ᴺ: the extra factor is not constant, so Θ(4ᴺ) ≠ Θ(2ᴺ). Constants in exponents matter; constants in front don’t.

5.2The two sums you need

Big idea

Most runtime problems reduce to adding up the work of each loop iteration or each recursive call. Two sums do almost all the work: the arithmetic sum (each term grows by a fixed amount) and the geometric sum (each term grows by a fixed factor).

1 + 2 + 3 + ⋯ + N = N(N + 1)/2 ∈ Θ(N²)Arithmetic. Pair the first and last terms: N + 1, N pairs of half. Roughly “N terms averaging N/2.”
1 + 2 + 4 + ⋯ + N = 2N − 1 ∈ Θ(N)Geometric with ratio 2 (N a power of 2). Check: 1 + 2 + ⋯ + 1024 = 2047. The last term is at least half the total.

Why the geometric sum is only Θ(last term): each term is double the previous, so the last term is bigger than all earlier terms combined (1024 > 1 + 2 + ⋯ + 512 = 1023). The total is between “last term” and “twice the last term.” This holds for any ratio > 1: the sum is Θ(largest term). It also works shrinking: N + N/2 + N/4 + ⋯ + 1 < 2N.

5.3Nested loops with tricky bounds

Big idea

Don’t multiply “outer loop length × inner loop length” blindly. That shortcut only works when the inner loop’s length doesn’t depend on the outer variable. The safe method: for each value of the outer variable, write how many times the inner body runs, then add those numbers.

  1. List the values the outer variable takes (0, 1, …, N−1? or 1, 2, 4, …?).
  2. For each, count the inner iterations as a formula in that variable.
  3. Add them up with a sum from 5.2. Sanity-check with a small N.
Example · triangle loop 
for (int i = 0; i < N; i++)
    for (int j = i; j < N; j++)
        count++;
  1. When i = 0 the inner body runs N times; i = 1 gives N − 1; …; i = N − 1 gives 1.
  2. Total: N + (N−1) + ⋯ + 1 = N(N+1)/2. For N = 64 that’s 2080 (checked by running it).
  3. Θ(N²). Starting j at i only halves the work; it doesn’t change the growth.
Example · outer doubles, inner goes up to i 
for (int i = 1; i < N; i *= 2)
    for (int j = 0; j < i; j++)
        count++;
  1. Outer values: i = 1, 2, 4, …, up to below N, about log₂N of them.
  2. Inner runs i times, so the total is 1 + 2 + 4 + ⋯ + N/2.
  3. Geometric, so Θ(N). For N = 1024 the count is exactly 1023.

The tempting wrong answer is “log N outer × up to N inner = N log N.” That overcounts because most outer iterations are cheap.

Example · inner doubles, outer is linear 
for (int i = 0; i < N; i++)
    for (int j = 1; j < N; j *= 2)
        count++;
  1. The inner loop never looks at i: it always runs log₂N times.
  2. Here multiplying is fine: N · log₂N. For N = 1024: 10,240.
  3. Θ(N log N).
Example · square-root bound 
for (int i = 1; i * i < N; i++)
    count++;
  1. The loop stops once i² ≥ N, i.e. once i ≥ √N.
  2. So it runs about √N times (N = 1024 → 31 times). Θ(√N).

for (int i = N; i > 0; i /= 2)
    for (int j = 0; j < i; j++)

5.4Recursion trees

Big idea

For a recursive method, draw the tree of calls. Each node is one call; write next to it the work that call does besides its recursive calls. The total runtime is the sum of all those numbers. Add level by level: (nodes on the level) × (work per node), then add the levels.

  1. Write the recurrence: e.g. “a call on size N makes 2 calls on size N/2 and does N work itself.”
  2. Level k: how many nodes (often 2ᵏ), what size each (N/2ᵏ or N − k), what work each?
  3. How many levels until size hits the base case (log₂N for halving, N for subtracting 1)?
  4. Sum over levels, using 5.2.
Example · two halves, linear work: T(N) = 2T(N/2) + N 
static int k(int n) {
    if (n <= 1) return 1;
    for (int i = 0; i < n; i++) { /* Θ(1) */ }
    return k(n / 2) + k(n / 2);
}
  1. Level 0: 1 call of size N, work N. Level 1: 2 calls of size N/2, total N. Level 2: 4 × N/4 = N.
  2. Every level costs N in total. There are log₂N levels before size 1.
  3. Total ≈ N log₂N, so Θ(N log N). (Mergesort has exactly this shape.) Counted in Java for N = 1024: 11,264 = 1024·10 + 1024 leaves.

5.5Amortized analysis

Big idea

Some operations are usually cheap but occasionally very expensive. Amortized cost asks: over any long sequence of operations, what is the average cost per operation? If N operations cost Θ(N) in total, each one is amortized Θ(1), even if a few of them individually cost Θ(N).

The standard example is the resizing array list (AList). addLast is Θ(1) until the array is full; then you allocate a bigger array and copy every item, which costs Θ(size).

Example · copies made while adding 1000 items, starting at capacity 1
  1. Grow by ×2: resizes happen at sizes 1, 2, 4, …, 512. Copies = 1 + 2 + 4 + ⋯ + 512 = 1023. Less than 2 copies per add: amortized Θ(1).
  2. Grow by +10: resizes at sizes 1, 11, 21, …, 991. Copies = 49,600 (from a simulation). That’s about N²/20: Θ(N²) total, so amortized Θ(N) per add.

Why multiplying works: the “bank account” view

Charge each addLast 3 coins instead of 1. One coin pays for writing the item; two are saved. Right after resizing from capacity C to 2C, the account is empty; by the time the next C adds fill the array, C × 2 = 2C coins have been saved, enough to pay to copy all 2C items at the next resize. The balance never goes negative, so the true total is at most 3N: Θ(1) amortized.

With +10 growth, only 10 cheap adds happen between resizes, but each resize costs the current size. No fixed number of coins per add can keep up.

Trap

Amortized Θ(1) is not “every operation is Θ(1).” A single addLast that triggers a resize is still Θ(N). Also, if you shrink, don’t halve the array as soon as it’s half full: alternating add/remove at that boundary would resize every time. Shrink when it’s about a quarter full instead.

5.6Best case vs worst case

Big idea

For a fixed size N, different inputs can take different amounts of time. The worst case is the slowest input of size N; the best case is the fastest. Each case is its own function of N and gets its own Θ.

static boolean contains(int[] a, int x) {
    for (int i = 0; i < a.length; i++)
        if (a[i] == x) return true;
    return false;
}
  • Best case: x is at index 0. Θ(1).
  • Worst case: x is absent. Θ(N).
  • Overall: you can’t write a single Θ. Say “O(N) and Ω(1),” or give both cases.

The best case must still be for large N. “The best case is when the array is empty” is wrong: N is fixed and large, and you choose the luckiest arrangement of those N items.

Trap

“O(N) means worst case, Ω(N) means best case” is a common mix-up. Correct statements: “the worst-case runtime is Θ(N)”, “the runtime is O(N)” (true for all inputs), “the best-case runtime is Θ(1).” Saying “the runtime is Ω(N)” here would be false, because some inputs finish in constant time.

A method loops for i in 0..N-1, and inside, if a[i] < 0, it runs a second full loop over the array (and doesn’t return). Best and worst case?tap

Best: Θ(N) (no negatives: just the outer loop). Worst: Θ(N²) (all negative: N inner loops of N). So the runtime is O(N²) and Ω(N).

Unit B6 · Disjoint sets

Four versions of one tiny data structure, each fixing the previous one’s weakness. The punchline is a tree that can never get tall.

6.1The problem and Quick Find

Big idea

We have items 0 … N−1. We want two operations: connect(p, q) merges the groups containing p and q, and isConnected(p, q) asks whether p and q are in the same group. Connections are transitive: connect(0,1) then connect(1,2) means 0 and 2 are connected. We never disconnect.

The trick shared by all versions: we don’t store the individual connections. We only store which group each item is in, since that’s all isConnected needs.

Quick Find

Keep an array id where id[i] is a group label. Two items are connected iff they have the same label.

  • isConnected(p, q): compare id[p] == id[q]. Θ(1).
  • connect(p, q): relabel every item that has p’s label to q’s label. Must scan the whole array: Θ(N).

connect(2,3) id = [1, 1, 3, 3, 4, 5]
connect(0,3) id = [3, 3, 3, 3, 4, 5]

The last connect had to find and relabel both 0 and 1. With N items, N connects cost Θ(N²).

6.2Quick Union

Big idea

Make connecting cheap by not relabeling everybody. Store each group as a tree: parent[i] is i’s parent, and a root is its own parent. The root is the group’s name. To connect, hang one root under the other: a single array write.

  • find(p) (also called root): follow parent pointers until you reach a node that is its own parent.
  • connect(p, q): parent[find(p)] = find(q).
  • isConnected(p, q): find(p) == find(q).

Both operations cost Θ(height of the tree). The problem: nothing stops the tree from becoming a long chain.

Example · the spindly disaster

Six items. connect(0,1), connect(1,2), connect(2,3), connect(3,4), connect(4,5), always putting the first root under the second.

parent = [1, 2, 3, 4, 5, 5]
0 → 1 → 2 → 3 → 4 → 5   (height 5)

Now find(0) walks the whole chain. In general height can reach N − 1, so worst-case find is Θ(N), and so is connect (it calls find).

Unit B7 · Search trees

BSTs give Θ(log N) search when they’re bushy and Θ(N) when they’re spindly. B-trees and LLRBs are two views of one fix: trees that stay balanced no matter what order you insert in.

7.1Binary search trees

Big idea

A sorted array gives fast binary search but slow inserts. A linked list gives fast inserts but slow search. A BST is a linked structure shaped like binary search itself: at each node you throw away one side.

BST property: for every node, all keys in its left subtree < its key < all keys in its right subtree“All keys in the subtree,” not just the immediate children. No duplicate keys.

Search and insert

Search: compare with the root, go left if smaller, right if larger, stop on a match or a null. Insert: search for the key; if you fall off at a null link, put the new node there. 61B writes insert recursively so that each call returns the (possibly new) root of its subtree:

static Node insert(Node t, int key) {
    if (t == null) return new Node(key);
    if (key < t.key)      t.left  = insert(t.left, key);
    else if (key > t.key) t.right = insert(t.right, key);
    return t;
}

The line t.left = insert(t.left, key) reassigns the link even when nothing changed. That’s harmless and is what makes the null case work: the new node gets attached to its parent on the way back up.

            50

       30        70
      /  \      /  \
    20    40   60   80
         /  \    \
        35  45    65

Runtime is all about height

Search and insert cost Θ(h), where h is the height. For N nodes, h ranges from about log₂N (bushy) to N − 1 (spindly). Inserting in sorted order gives the spindly case: 10, 20, 30, 40, 50 builds a chain going right. Inserting in random order gives height Θ(log N) on average, but we can’t choose the order our users insert in.

“BST operations are Θ(log N)” is false as a worst-case statement. Worst case is Θ(N). Also, checking only each node against its children doesn’t verify the BST property: a 55 in the left subtree of 50 (say, as the right child of 30) passes the local check but is illegal.

7.2Deletion (Hibbard)

Big idea

Deleting a node with two children leaves a hole that must be filled by a key that still fits between the left and right subtrees. Exactly two keys work: the largest key on the left (predecessor) or the smallest key on the right (successor). Either of those has at most one child, so removing it from its old spot is easy.

  1. No children: just remove it (parent’s link becomes null).
  2. One child: the parent’s link skips over it and points to its only child.
  3. Two children: copy the successor’s key (go right once, then left as far as possible) into this node, then delete the successor from the right subtree (it’s case 1 or 2).

7.3B-trees (2-3 and 2-3-4 trees)

Big idea

BSTs get tall because new leaves keep hanging deeper. A B-tree never adds a new leaf below the others. New keys are stuffed into an existing leaf; when a node overflows, it splits and pushes a key up. The tree only grows taller when the root splits, which lifts every leaf by one together. So every leaf is always at the same depth: perfectly balanced.

Definitions

  • Each node holds up to L sorted keys and has (number of keys + 1) children.
  • 2-3 tree (L = 2): nodes have 1 key/2 children or 2 keys/3 children. 2-3-4 tree (L = 3): up to 3 keys and 4 children.
  • Children are ordered like a BST: in node [a b], the left child holds keys < a, the middle child keys between a and b, the right child keys > b.

Insertion

  1. Walk down as in a BST to the correct leaf and add the key there, keeping it sorted.
  2. If the leaf now has L + 1 keys, split it: send one key up to the parent; the keys to its left and right become two separate nodes.
  3. For a 2-3 tree (3 keys after overflow) the middle key goes up. For a 2-3-4 tree (4 keys), 61B sends up the left-middle key (always check the convention a problem states).
  4. If the parent overflows, split it too, repeating upward. If the root splits, the pushed-up key becomes a new root: height + 1.

7.4LLRBs and rotations

Big idea

B-trees are balanced but awkward to code (nodes of different sizes, splitting). A left-leaning red-black tree is an ordinary BST that secretly is a 2-3 tree. Glue links are colored red: a 3-node [a b] is stored as two BST nodes, b with a as its left child, joined by a red link.

2-3 node [a b]          as an LLRB
 /   |   \                  b
x    y    z          (red) /  \
                          a    z
                         / \
                        x   y

The rules (and what they mean)

  • Red links lean left. That’s just how we chose to draw a 3-node.
  • No node has two red links touching it (no red parent-link plus red child-link, no two red children). That would glue three keys into one node (a 4-node), which a 2-3 tree doesn’t allow.
  • Every path from the root to a null link crosses the same number of black links. Black links are the real 2-3 tree edges, and all 2-3 leaves are at the same depth.

The correspondence is one-to-one: each 2-3 tree has exactly one LLRB and vice versa. Height: at most about 2 log₂N (every other link on a path could be red), so search is Θ(log N).

Notation on this page: a * after a key means the link from its parent to it is red.

Rotations

A rotation rearranges three nodes while keeping BST order. rotateLeft(h) makes h’s right child x the new subtree root, with h as x’s left child; x’s old left subtree B becomes h’s right subtree. rotateRight is the mirror image. The link between them keeps its color role: the new root takes h’s old link color and h becomes red.

rotateLeft(h):
    h                 x
   / \               / \
  A   x*     →     h*   C
     / \          / \
    B   C        A   B

    Node x = h.right;
    h.right = x.left;
    x.left = h;
    x.color = h.color;
    h.color = RED;
    return x;
}
Trap

Rotation preserves the BST in-order sequence: A < h < B < x < C before and after. If your rotated tree reads differently left to right, you moved B to the wrong place. B always switches parents.

  2. If the left child is red and its left child is also red: rotateRight (two reds in a row → balance them).
  3. If both children are red: color flip (children turn black, this node’s link turns red). This is a 2-3 split: the middle key moves up into its parent.

A priority queue only ever needs the smallest item, so it doesn’t need a fully sorted structure. A heap is the cheapest shape that keeps the minimum on top. Then: the four standard ways to walk a tree.

8.1Priority queues and the heap shape

Big idea

A min priority queue supports add(x), getSmallest(), removeSmallest(), and size(). A binary min-heap stores it as a tree that is (1) complete: every level full except possibly the last, which fills left to right; and (2) heap-ordered: every node is ≤ each of its children. So the minimum is always the root.

Heap order is much weaker than BST order. Siblings can be in any order, and nothing is said about left vs right. That weakness is what makes updates cheap.

Array representation

Because the tree is complete, there are no gaps when you read it level by level, left to right. So store it in an array. 61B leaves index 0 empty and puts the root at index 1:

8.2Insert (swim) and removeSmallest (sink)

Big idea

Each operation first keeps the shape correct (put the new item at the end / move the last item to the root), which may break heap order along a single root-to-leaf path. Then it fixes order by swapping along that path. Paths have length ≤ log₂N, so both cost Θ(log N).

  1. add(x): place x at the next free index (end of array). Swim: while x is smaller than its parent, swap them.
  2. removeSmallest(): save the root. Move the last item to the root and shrink the size by 1. Sink: while it’s bigger than a child, swap it with the smaller child.

8.3Tree traversals

Big idea

A traversal visits every node once. The three depth-first orders differ only in when you visit a node relative to its two subtrees. Level order instead goes top to bottom, one depth at a time.

  • Preorder: visit node, then left subtree, then right subtree.
  • Inorder: left subtree, visit node, right subtree. On a BST this gives sorted order.
  • Postorder: left subtree, right subtree, then visit node.
  • Level order: depth 0, then depth 1 left to right, then depth 2, … (uses a queue).

9.1Graph vocabulary

Big idea

A graph is a set of things (vertices) plus a set of pairwise connections (edges). Maps, social networks, course prerequisites and mazes are all graphs, so one toolbox covers all of them.

G = (V, E)V = set of vertices, E = set of edges. We write V and E for their sizes too. A simple graph has no self-loops and no duplicate edges, so E ≤ V².
  • Undirected: edge {u, v} goes both ways. Directed (digraph): edge u → v goes one way only.
  • Weighted: each edge carries a number (length, cost, time).
  • Adjacent / neighbors: u and v share an edge. Degree of v = number of edges touching v (in a digraph: out-degree and in-degree).
  • Path: sequence of vertices joined by edges. Cycle: path that returns to its start (with at least one edge, no repeated edges).
  • Connected (undirected): every vertex can reach every other. A connected component is a maximal connected piece.
  • Tree: connected and acyclic. A tree on V vertices has exactly V − 1 edges.
  • DAG: directed acyclic graph (no directed cycle).

Handy fact: in an undirected graph the degrees add up to 2E, because every edge is counted once from each end. This is why “visit every vertex and look at all its neighbors” costs Θ(V + E), not Θ(V · E).

Trap

Trees are graphs, but a graph traversal must remember which vertices it has already marked. A tree traversal never needs this because there is only one way to reach each node; a graph with cycles would make an unmarked traversal loop forever.

9.3Depth-first search

Big idea

DFS is “go as deep as you can, then back up.” From v, mark v, then recursively visit each unmarked neighbor in order. It answers reachability (can s reach t?) and its bookkeeping gives paths, components, cycles and topological order.

void dfs(int v) {
    marked[v] = true;
    // preorder: record v here
    for (int w : adj(v)) {
        if (!marked[w]) {
            edgeTo[w] = v;  // how we first reached w
            dfs(w);
        }
    }
    // postorder: record v here
}
  • DFS preorder: the order vertices get marked (first entered).
  • DFS postorder: the order vertices finish (all neighbors done, call returns).
  • edgeTo[w] = the vertex we came from. Following edgeTo backward from t to s rebuilds a path (not necessarily the shortest).

9.4Breadth-first search

Big idea

BFS explores in rings: first everything 1 edge from s, then everything 2 edges away, and so on. A queue (first in, first out) enforces the rings. The payoff: BFS finds paths with the fewest edges.

Queue<Integer> q = new ArrayDeque<>();
q.add(s); marked[s] = true; distTo[s] = 0;
while (!q.isEmpty()) {
    int v = q.remove();
    for (int w : adj(v)) {
        if (!marked[w]) {
            marked[w] = true;      // mark when ENQUEUED
            edgeTo[w] = v;
            distTo[w] = distTo[v] + 1;
            q.add(w);
        }
    }
}

9.5DAGs and topological sort

Big idea

A topological order lists the vertices of a DAG so that every edge points forward (u before v whenever u → v). Think “a legal order to take classes given prerequisites.” Recipe: run DFS from every unmarked vertex and output the reverse of the postorder.

topological order = reverse DFS postorderExists if and only if the digraph has no directed cycle. Usually not unique.

Why it works

Take any edge u → v. Either DFS reaches v while u is still on the call stack (then v finishes before u, because u can’t finish until its call to v returns), or v was already finished. v can’t be on the stack while u is visited, because then v ⇝ u ⇝ v would be a cycle. In both remaining cases v finishes before u, so in reversed postorder u comes first.

Example · DAG trace

Edges 0→1, 0→2, 1→3, 2→3, 3→4, 5→2, 5→6, 6→4. Outer loop tries vertices 0, 1, …, 6; neighbors ascending.

  1. dfs(0) → dfs(1) → dfs(3) → dfs(4). 4 has no out-edges: post 4. Then post 3, post 1.
  2. Back in 0: dfs(2). Its neighbor 3 is marked: post 2. Then post 0.
  3. Outer loop: 1–4 marked; 5 isn’t → dfs(5). 2 marked; dfs(6): 4 marked, post 6. post 5.
postorder: 4 3 1 2 0 6 5

Check: every edge goes left to right (e.g. 5→2: 5 is first; 6→4: 4 is last).

Runtime Θ(V + E). Another valid method (Kahn’s algorithm): repeatedly remove a vertex with in-degree 0. Both are fine; exams usually ask for the DFS version.

You must restart DFS from every unmarked vertex. Starting only at 0 above would never visit 5 or 6. And use postorder reversed, not preorder: preorder 0 1 3 4 2 5 6 puts 2 after 3, breaking edge 2→3.

9.6Cycle detection (and other graph problems)

Big idea

A cycle shows up during DFS as an edge back to a vertex you are still in the middle of. The exact test differs for directed and undirected graphs.

  • Directed: keep an onStack flag (set on entering v, cleared when v finishes). If you see an edge v → w with w on the stack, there is a cycle. Seeing a finished marked vertex is fine (that’s just two paths meeting, like 0→1→3 and 0→2→3).
  • Undirected: during DFS, seeing a marked neighbor that is not the vertex you came from means a cycle. Alternative: add edges one at a time to a disjoint-sets structure; if an edge joins two vertices already connected, it closes a cycle.
Example · add edge 4→1 to the 9.5 DAG
  1. dfs(0) puts 0 on the stack, then 1, then 3, then 4.
  2. At 4 we see edge 4→1, and 1 is on the stack (0, 1, 3, 4). Cycle found: 1 → 3 → 4 → 1.
  3. Without that edge, at 2 we see 2→3 with 3 already finished: no cycle, as expected for a DAG.

Easy vs hard graph problems

Many problems are DFS/BFS in disguise: s–t connectivity, connected components, bipartiteness (2-color with BFS), cycle detection, topological sort, Euler tour (use every edge once; exists iff all degrees are even, for a connected graph). Others with similar descriptions have no known efficient algorithm, like the Hamiltonian tour (visit every vertex once).

Trap

In a digraph, “marked neighbor” alone does not mean a cycle. Only an edge back to a vertex on the current DFS path does.

10.1Dijkstra’s algorithm

Big idea

Visit vertices in order of their current best-known distance from the source, using a priority queue. Each time you visit v, “relax” its out-edges: see if going through v gives a neighbor a shorter route. With non-negative weights, the vertex you pull out is always final.

relax(v → w, weight c): if distTo[v] + c < distTo[w], set distTo[w] = distTo[v] + c, edgeTo[w] = v, and lower w’s prioritydistTo[v] = best distance found so far; edgeTo[w] = previous vertex on that best path. The edgeTo arrows form the shortest-paths tree (SPT).
  1. distTo[s] = 0, every other distTo = ∞. Put all vertices in a PQ keyed by distTo.
  2. Remove the vertex v with the smallest distTo. It is now visited (final).
  3. Relax every edge out of v. Repeat until the PQ is empty.

10.2Why Dijkstra works, and negative edges

Big idea

When v has the smallest distTo among unvisited vertices, any other route to v must leave the visited region through some unvisited vertex u with distTo[u] ≥ distTo[v], and then only add non-negative edges. So nothing can beat distTo[v]. A negative edge breaks the “only add” part.

Example · a negative edge fools Dijkstra

Edges A→B 1, A→C 3, C→B −3, B→D 1. True shortest distance to D: A→C→B→D = 3 − 3 + 1 = 1.

  1. Pop A: B = 1, C = 3.
  2. Pop B (1), declared final. Relax B→D: D = 2.
  3. Pop D (2), final, with the wrong answer 2.
  4. Pop C (3): C→B gives 0 < 1, but B was already processed, so D never hears about it. Dijkstra reports D = 2.
Trap

“Add a big constant to every weight to make them positive” does not fix it. Adding 3 to each edge above makes A→B (4) cheaper than A→C→B (6 + 0 = 6), so the shortest path changes. Paths with more edges get penalized more.

Negative edges are fine for Bellman–Ford (not tested in depth) and for DAGs (next section). A negative cycle makes “shortest path” undefined.

10.4A* search

Big idea

Dijkstra explores in all directions. If you only care about one goal and have a guess h(v) of the remaining distance from v to the goal, visit vertices in order of distTo[v] + h(v) instead. Good guesses steer the search toward the goal; stop when the goal is popped.

priority(v) = distTo[v] + h(v)h ≡ 0 gives exactly Dijkstra. Example heuristic on a map: straight-line distance to the goal.
  • Admissible: h(v) ≤ true distance from v to the goal, for every v. Never overestimates.
  • Consistent: h(v) ≤ c(v, w) + h(w) for every edge v → w, and h(goal) = 0. The guess never drops by more than the edge you just walked (a triangle inequality). Consistent ⇒ admissible.

For the graph version taught in 61B (each vertex is finalized once when popped), consistency guarantees the right answer. Admissibility alone is not enough.

Example · admissible but inconsistent heuristic gives a wrong answer

Edges S→A 1, S→B 1, A→C 1, B→C 2, C→G 3. True distance S→G = 5 (S A C G). Heuristic h(S)=0, h(A)=4, h(B)=1, h(C)=0, h(G)=0. Admissible: true distances to G are A 4, B 5, C 3, so no overestimate. Inconsistent: h(A) = 4 > c(A,C) + h(C) = 1.

  1. Pop S. A: 1 + 4 = 5. B: 1 + 1 = 2.
  2. Pop B (2). C: distTo 3, priority 3 + 0 = 3.
  3. Pop C (3). C is finalized at 3, but the true distance is 2. G: distTo 6.
  4. Pop A (5): A→C would give 2, too late. Pop G: reports 6, wrong.

Change h(C) to 3 (now consistent): after B, C’s priority is 6, so A (5) is popped first, sets C to 2, and G is reached with the correct 5.

Trap

A* only gives the right distance to the goal. Other vertices may never be visited or may hold non-final distTo values when it stops. It is not a replacement for a full shortest-paths tree.

Is h(v) = 0 for all v admissible? Consistent? What does A* become?tap

Both (0 never overestimates, and 0 ≤ c + 0 since weights are non-negative). A* becomes plain Dijkstra, stopping when the goal is popped.

10.5MSTs and the cut property

Big idea

A minimum spanning tree (MST) of a connected, undirected, weighted graph is a set of edges that connects all vertices, has no cycles, and has the smallest possible total weight. Every MST algorithm is built on one fact: the lightest edge across any cut is in the MST.

Cut property: for any cut, the minimum-weight crossing edge belongs to the MSTA cut splits V into two non-empty groups. A crossing edge has one end in each group. (Assumes distinct weights; with ties, it belongs to some MST.)

Why it’s true

Suppose the lightest crossing edge e is not in the MST T. Adding e to T creates a cycle. That cycle crosses the cut once on e, so it must cross back on some other edge f, which is heavier than e. Remove f: still a spanning tree, and lighter than T. Contradiction.

  • An MST has exactly V − 1 edges.
  • With all weights distinct, the MST is unique.
  • Cycle property (the mirror fact): the heaviest edge on any cycle is not in the MST.
Trap

An MST is not a shortest-paths tree. Triangle with A–B 3, B–C 3, A–C 5: the MST is {A–B, B–C} (total 6), but the shortest path from A to C is the direct edge of weight 5, which the MST leaves out.

True or false: the single heaviest edge in a graph is never in its MST.tap

False. If that edge is a bridge (the only connection to some vertex), every spanning tree must use it. The correct statement is about the heaviest edge on a cycle.

10.6Prim’s algorithm

Big idea

Grow one tree from a start vertex. At each step add the lightest edge leaving the tree. The cut is (tree, everything else), so the cut property says that edge is safe. Implementation: Dijkstra’s code with one change: a vertex’s priority is the weight of the best single edge connecting it to the tree, not its distance from the source.

10.7Kruskal’s algorithm

Big idea

Sort all edges by weight. Go through them lightest first; keep an edge unless it would make a cycle. A disjoint-sets (weighted quick union) structure answers “are these endpoints already connected?” fast.

Why it’s correct

When Kruskal accepts edge u–v, u and v are in different components. Cut = (u’s component, everything else). Every lighter edge was already considered, and any lighter crossing edge would have been accepted and merged things, so u–v is the lightest crossing edge. Cut property → safe.

11.1From arrays to hash tables

Big idea

An array lookup is Θ(1) because you jump straight to an index. Hashing turns any key into an index: compute an integer from the key (its hash code), then reduce it into the range 0 … M−1. Different keys can land in the same spot (a collision), so each spot holds a small list.

  1. Compute h = key.hashCode() (any int, possibly negative).
  2. Reduce: bucket = Math.floorMod(h, M), a number from 0 to M − 1.
  3. Search, insert or delete inside that bucket only, using equals to compare keys.

Why not just make an array as big as all possible keys? There are 232 ints and infinitely many strings. Hashing trades a little collision handling for using only Θ(N) memory.

Trap

Java’s % keeps the sign of the left side: -5 % 4 is −1, not a valid index. Use Math.floorMod(-5, 4), which is 3. And Math.abs(h) % M is also broken: Math.abs(Integer.MIN_VALUE) is still negative (−2147483648).

11.4The equals/hashCode contract and good hash codes

Big idea

A hash table looks only in the bucket chosen by hashCode, then uses equals inside it. So objects that are equal must have equal hash codes, or the table looks in the wrong bucket.

a.equals(b) ⟹ a.hashCode() == b.hashCode()The converse is not required: equal hash codes may belong to unequal objects (collisions). Override both or neither.

A valid hashCode obeys the contract and is deterministic (same object, same answer, as long as fields used by equals don’t change). A good one also spreads keys evenly across buckets and is fast to compute.

class Pt {
    int x, y;
    Pt(int x, int y) { this.x = x; this.y = y; }
    @Override public boolean equals(Object o) {
        if (!(o instanceof Pt p)) return false;
        return x == p.x && y == p.y;
    }
    // no hashCode override!
}
Set<Pt> s = new HashSet<>();
s.add(new Pt(1, 2));
System.out.println(new Pt(1, 2).equals(new Pt(1, 2)));
System.out.println(s.contains(new Pt(1, 2)));

Prints true then false. The two Pt objects are equal, but they use Object’s identity-based hashCode, so the lookup almost surely goes to a different bucket and never calls equals. Adding public int hashCode() { return Objects.hash(x, y); } makes contains print true.

“Valid” and “good” are different exam questions. return 0 is perfectly valid (correct results), just slow. A hashCode that ignores some fields used by equals is still valid; one that uses a field equals ignores is not.

11.5Mutable keys

Big idea

An item is filed in the bucket its hash code pointed to when it was inserted. If you then change the key so its hash code changes, the item is stranded in the old bucket and lookups go to the new one.

12.2Prefix operations

Big idea

All keys starting with a prefix live in one subtree. Walk down to the prefix’s node, then explore below it. Hash tables can’t do this at all, and BSTs do it less directly.

  • keysWithPrefix(p): walk to p’s node (return nothing if missing), then DFS its subtree, collecting every marked node’s string. Visiting children in alphabetical order lists results alphabetically.
  • longestPrefixOf(q): walk down following q’s characters; remember the last marked node passed; stop when a link is missing or q runs out.
Example · using the 12.1 trie

  5. longestPrefixOf("awlsome"): a* (“a”), w, l, s* (“awls”), no o child → "awls".
  6. longestPrefixOf("awl"): last marked node passed is a → "a".

13.1Sorting vocabulary

Big idea

Every sort is judged on the same four questions: how many steps in the best and worst case, how much extra memory, and whether equal items keep their original order.

A sort rearranges a sequence so it is in order under some total order (for objects, compareTo or a Comparator). A comparison sort only learns about the items by asking “is a < b?”, never by looking inside them. Everything in this unit is a comparison sort; Unit B14 ends with sorts that peek at digits.

  • Inversion: a pair of positions i < j whose items are in the wrong order (a[i] > a[j]). A sorted array has 0 inversions; a reversed array of n items has the maximum, n(n−1)/2. Sorting is the job of removing every inversion.
  • In-place: uses only Θ(1) extra memory (some people allow Θ(log n) for a recursion stack).
  • Stable: items that compare equal come out in the same relative order they went in.
Example · counting inversions

[1, 2, 4, 3, 5, 7, 6] has exactly 2 inversions: (4, 3) and (7, 6). [5, 4, 3, 2, 1] has every pair inverted: 5·4/2 = 10.

How many inversions does [6, 3, 9, 1, 5, 2] have?tap

10. Count, for each item, the smaller items to its right: 6 → {3, 1, 5, 2} = 4; 3 → {1, 2} = 2; 9 → {1, 5, 2} = 3; 1 → 0; 5 → {2} = 1; 2 → 0. Total 4 + 2 + 3 + 1 = 10. (We use this array in every trace below.)

13.2Selection sort

Big idea

Find the smallest remaining item and swap it to the front of the unsorted part. Repeat. The front grows into the final sorted answer one item at a time.

  1. For i = 0, 1, …, n−2: scan positions i..n−1 for the minimum.
  2. Swap it into position i. Positions 0..i are now final.
Example · selection sort on [6, 3, 9, 1, 5, 2] 
start   6 3 9 1 5 2
pass 1  1 3 9 6 5 2   min 1 swapped with 6
pass 2  1 2 9 6 5 3   min 2 swapped with 3
pass 3  1 2 3 6 5 9   min 3 swapped with 9
pass 4  1 2 3 5 6 9   min 5 swapped with 6
pass 5  1 2 3 5 6 9   min 6 already in place

Why it takes Θ(n²) always

Pass i must look at every remaining item to be sure it found the minimum, no matter how sorted the input already is. That is (n−1) + (n−2) + ⋯ + 1 = n(n−1)/2 comparisons, so Θ(n²) in the best and worst case. It does only Θ(n) swaps, which is its one selling point.

Trap

Selection sort is not stable. The long-distance swap can jump an item over its equal twin. Sort [2x, 2y, 1] by number: pass 1 swaps 1 with 2x, giving [1, 2y, 2x]. The two 2s flipped.

After 2 passes of selection sort on [4, 8, 2, 7, 1], what is the array?tap

[1, 2, 8, 7, 4]. Pass 1: min 1 swaps with 4 → [1, 8, 2, 7, 4]. Pass 2: min of [8, 2, 7, 4] is 2, swap with 8 → [1, 2, 8, 7, 4]. The tell-tale sign of selection sort: the prefix holds the globally smallest items, in order, and the rest is scrambled.

13.3Insertion sort

Big idea

Keep a sorted prefix. Take the next item and slide it left, swapping past every larger neighbor, until it sits in the right place. Like sorting a hand of cards.

for (int i = 1; i < a.length; i++)
    for (int j = i; j > 0 && a[j-1] > a[j]; j--)
        swap(a, j, j - 1);
Example · insertion sort on [6, 3, 9, 1, 5, 2] 
start  6 3 9 1 5 2
i=1    3 6 9 1 5 2   3 slides past 6       (1 swap)
i=2    3 6 9 1 5 2   9 stays               (0 swaps)
i=3    1 3 6 9 5 2   1 slides past 9,6,3   (3 swaps)
i=4    1 3 5 6 9 2   5 slides past 9,6     (2 swaps)
i=5    1 2 3 5 6 9   2 slides past 9,6,5,3 (4 swaps)
total swaps = 10 = number of inversions

Why swaps = inversions

Each swap exchanges two adjacent items that are out of order. That fixes exactly one inversion (that pair) and leaves every other pair’s order unchanged. The algorithm stops when no inversions remain. So the number of swaps is exactly the number of inversions k in the input.

insertion sort = Θ(n + k)n for the outer loop (each item is at least looked at), k for the swaps. Best case (sorted, k = 0): Θ(n). Worst case (reversed, k = n(n−1)/2): Θ(n²).
  • Stable: an item stops as soon as its left neighbor is ≤ it, so it never jumps over an equal item (the test is strictly >).
  • In-place, Θ(1) extra memory.
  • Fastest in practice for small arrays (roughly n < 15) and for almost sorted arrays. Real library sorts switch to insertion sort for small pieces.
Trap

“Almost sorted” means few inversions, not “most items in place”. If each item is at most d positions from where it belongs, there are at most about nd inversions, so insertion sort is Θ(nd), which is linear for constant d.

13.4Heapsort

Big idea

Selection sort spends Θ(n) finding each max. A max-heap finds it in Θ(log n). So: turn the array into a max-heap in place, then repeatedly swap the max to the end and repair the heap.

Here the heap uses 0-indexed positions: children of index k are 2k+1 and 2k+2. (61B’s PQ lecture uses 1-indexed with the root at 1; the idea is identical, only the index arithmetic changes.)

  1. Bottom-up heapify: for k from the last non-leaf (n/2 − 1) down to 0, sink k (swap it with its larger child until it is ≥ both children). Leaves are already tiny heaps, so start above them.
  2. Sort-down: repeat n−1 times: swap the root (the max) with the last item of the heap, shrink the heap by one, sink the new root.
Example · heapsort on [6, 3, 9, 1, 5, 2]

Heapify (last non-leaf is index 2):

sink(2): 9 >= child 2      6 3 9 1 5 2
sink(1): 3 < child 5, swap 6 5 9 1 3 2
sink(0): 6 < child 9, swap 9 5 6 1 3 2   max-heap!

Sort-down (heap | sorted part):

swap 9 to end, sink 2   6 5 2 1 3 | 9
swap 6 to end, sink 3   5 3 2 1 | 6 9
swap 5 to end, sink 1   3 1 2 | 5 6 9
swap 3 to end, sink 2   2 1 | 3 5 6 9
swap 2 to end           1 | 2 3 5 6 9

Why it works and what it costs

  • Invariant: the front is a valid max-heap, the back holds the largest items in sorted order. Each swap moves the current max to its final spot.
  • Each sink is O(log n) (heap height), done n times: Θ(n log n) worst case. Bottom-up heapify alone is actually Θ(n) (most nodes are near the bottom and sink only a little), but the sort-down dominates.
  • Θ(1) extra space: the heap lives inside the input array.
  • Not stable: the long jumps (root to end) scramble equal items.
  • Best case Θ(n) only in the odd situation where all items are equal (every sink stops immediately).
  • In practice slower than mergesort/quicksort because jumping between k and 2k has bad cache behavior.
Trap

Heapsort uses a max-heap (so the max goes to the back) even though 61B’s MinPQ is a min-heap. Also, inserting items one by one into a new heap (top-down) needs Θ(n) extra space unless done in place, and is Θ(n log n) instead of bottom-up Θ(n).

13.5Mergesort

Big idea

Merging two already-sorted lists is easy and linear: repeatedly take the smaller front item. So split in half, sort each half recursively, merge.

Example · merging [3, 6, 9] and [1, 2, 5]
  1. Fronts 3 vs 1: take 1 → [1]
  2. 3 vs 2: take 2 → [1, 2]
  3. 3 vs 5: take 3 → [1, 2, 3]
  4. 6 vs 5: take 5 → [1, 2, 3, 5]. Right list empty.
  5. Copy the rest: [1, 2, 3, 5, 6, 9].

Each step does one comparison and places one item, so merging a + b items costs Θ(a + b).

Full recursion on [6, 3, 9, 1, 5, 2]: split into [6, 3, 9] and [1, 5, 2]; those sort (recursively) to [3, 6, 9] and [1, 2, 5]; the merge above finishes the job.

Runtime by recursion tree

Level 0 merges n items; level 1 has two merges of n/2 (total n); level 2 has four of n/4 (total n)… There are log₂ n levels, each costing Θ(n). Total Θ(n log n) in every case, because the splitting ignores the data.

  • Θ(n) extra space for the merge buffer (array version).
  • Stable, as long as ties go to the left list (if (L[i] <= R[j]) takes from the left).
Trap

Writing < instead of <= in the merge takes from the right on ties and breaks stability. Also: mergesort is not faster on already-sorted input (still Θ(n log n)) unless you add a “halves already in order” shortcut.

Spot the sort: after some steps on [6, 3, 9, 1, 5, 2], the array is [3, 6, 1, 9, 2, 5]. Which basic sort?tap

Mergesort (bottom-up), after the first round: every pair (6,3), (9,1), (5,2) has been sorted. Fingerprints: sorted runs of equal length 2, 4, … Insertion sort leaves a sorted prefix and an untouched suffix; selection sort leaves the globally smallest items at the front; heapsort leaves the largest at the back with a heap in front.

14.1Quicksort and partitioning

Big idea

Pick a pivot. Partition: put everything smaller on its left and everything larger on its right. Now the pivot is in its final position, and the two sides can be sorted independently, recursively.

To partition around pivot x means: rearrange so all items left of x are ≤ x and all items right of x are ≥ x. The sides themselves need not be sorted.

Simple 3-way partition (the lecture demo version)

Use the leftmost item as the pivot. Walk left to right, copying each item into one of three new lists: smaller, equal, larger. Concatenate. Because each list keeps arrival order, this version is stable, but it uses Θ(n) extra space.

Example · quicksort [5, 8, 1, 9, 3, 5, 7, 2] with 3-way partition 
[5 8 1 9 3 5 7 2]  pivot 5 -> [1 3 2] [5 5] [8 9 7]
  [1 3 2]          pivot 1 -> []      [1]   [3 2]
    [3 2]          pivot 3 -> [2]     [3]   []
  [8 9 7]          pivot 8 -> [7]     [8]   [9]
result: 1 2 3 5 5 7 8 9

Note the duplicate 5s both go to the middle and are never touched again.

Trap

“Partitioned” ≠ “sorted”. After the first partition, [1, 3, 2] is on the left of the 5s but not in order. Only the pivot(s) are guaranteed to be in their final spot.

14.2Hoare partitioning (in place)

Big idea

Two pointers walk toward each other. L (from the left) likes small items and stops at one that is too big. G (from the right) likes big items and stops at one that is too small. Swap the two misfits, keep going. When they cross, swap the pivot into G’s spot.

  1. Pivot p = leftmost item. L starts just right of it, G at the right end.
  2. L moves right while the item is < p (“L hates items ≥ p”).
  3. G moves left while the item is > p (“G hates items ≤ p”).
  4. If L and G haven’t crossed, swap their items and step both inward. Repeat.
  5. Once they cross, swap the pivot with the item at G. Pivot is now in its final place.
Example · Hoare partition of [5, 8, 1, 9, 3, 6, 7, 2], pivot 5 
index      0 1 2 3 4 5 6 7
start      5 8 1 9 3 6 7 2
L stops at 1 (8), G stops at 7 (2): swap
           5 2 1 9 3 6 7 8
L stops at 3 (9), G stops at 4 (3): swap
           5 2 1 3 9 6 7 8
L moves to 4, G moves to 3: crossed
swap pivot with index 3 (G)
           3 2 1 5 9 6 7 8   pivot 5 at index 3

Why stopping on equal items matters

Both pointers stop on items equal to the pivot and swap them. That spreads duplicates over both sides. If an array is all copies of one value, the pivot ends up near the middle, giving balanced Θ(n log n) instead of Θ(n²).

Trap

Hoare partitioning is not stable (the swaps fling items across the array), but it is in place. Exams often ask for “the array after one partition”: trace it exactly; don’t just write “smalls, pivot, bigs” in some order.

Hoare-partition [4, 7, 2, 6, 1, 3] (pivot 4). Final array?tap

14.3Quicksort runtime and pivot choice

Big idea

Quicksort is fast exactly when pivots split the array into reasonably balanced pieces. A partition costs Θ(size); the question is how deep the recursion goes.

  • Best case: pivot is always the median. Like mergesort: log₂ n levels × Θ(n) per level = Θ(n log n).
  • Worst case: pivot is always the min or max. Each partition peels off just one item: n + (n−1) + ⋯ + 1 = Θ(n²). With a leftmost pivot this happens on already sorted (or reversed) input. Sorting 1000 sorted items takes about 1000·999/2 ≈ 500,000 comparisons instead of ≈ 10,000.
  • Expected (random order or random pivot): Θ(n log n), about 1.39 n log₂ n comparisons.

Why the expected case is n log n (intuition)

Call a pivot “good” if it lands in the middle half of its sub-array; that happens with probability 1/2. After a good pivot, every piece is at most 3/4 the size. So along any path from the top of the recursion, a piece shrinks by 3/4 about every 2 levels, reaching size 1 after O(log n) levels. Each level of recursion does Θ(n) total partition work. Even a consistently lopsided 10%/90% split still gives depth log10/9 n = Θ(log n).

Avoiding the worst case

  • Shuffle the array first (or pick a random pivot): the bad case becomes astronomically unlikely, for every input.
  • Median of three (first, middle, last): fixes sorted input cheaply, but crafted inputs can still be bad.
  • Exact median as pivot (via a linear-time selection algorithm): guarantees Θ(n log n) but the constant is so large it’s slower in practice.
  • Introsort: run quicksort, but switch to heapsort if recursion gets too deep. Worst case Θ(n log n).

Why quicksort beats mergesort in practice: in-place, tight inner loop, sequential memory access, fewer data moves.

Trap

“Quicksort is Θ(n log n)” is wrong as a worst-case statement. Its worst case is Θ(n²); its expected (and best) case is Θ(n log n). Also, a naive 2-way partition that sends all equal items to one side is Θ(n²) on an all-duplicates array.

Quicksort with leftmost pivot (no shuffle) on [1, 2, 3, …, n]. How many comparisons, and what is the recursion depth?tap

The pivot is always the minimum, so each call leaves an empty left side and a right side of size one less. Comparisons: (n−1) + (n−2) + ⋯ + 1 = n(n−1)/2 = Θ(n²). Depth Θ(n) (which can also overflow the call stack for big n).

14.4Quickselect

Big idea

To find the k-th smallest item (e.g. the median), partition once. The pivot lands at its true sorted index j. If j = k, done; otherwise recurse into only the one side that contains index k.

Example · 5th index (0-based) of [5, 8, 1, 9, 3, 5, 7, 2]
  1. Pivot 5: smaller [1, 3, 2] (indices 0–2), equal [5, 5] (3–4), larger [8, 9, 7] (5–7). Index 5 is in “larger”, at position 5 − 5 = 0 there.
  2. [8, 9, 7], want index 0. Pivot 8: smaller [7]. Index 0 is in “smaller”.
  3. [7]: the pivot itself. Answer 7. Check: sorted is 1 2 3 5 5 7 8 9.
expected Θ(n) · worst Θ(n²)With balanced pivots the work is n + n/2 + n/4 + ⋯ ≤ 2n: a geometric sum, because you recurse on one half, not both. Bad pivots every time give n + (n−1) + ⋯ = Θ(n²).
Why is quickselect expected Θ(n) while quicksort is Θ(n log n)?tap

Quicksort recurses on both sides, so every level of the recursion does Θ(n) total work across log n levels. Quickselect follows one side, so the level sizes shrink geometrically: n + n/2 + n/4 + ⋯ = Θ(n).

14.5Why comparison sorts need Ω(n log n)

Big idea

A comparison sort must tell apart all n! possible orderings of the input. Each yes/no comparison can at best cut the remaining possibilities in half. So it needs at least log₂(n!) comparisons, and log₂(n!) is Θ(n log n).

The decision tree argument

  1. Picture the algorithm as a binary tree: each internal node is a comparison “a < b?”, each leaf is a final answer (a particular reordering).
  2. Every one of the n! input orders must reach a different leaf (if two different orders reached the same leaf, the algorithm would apply the same rearrangement to both and get one of them wrong). So ≥ n! leaves.
  3. A binary tree of height h has at most 2h leaves. So 2h ≥ n!, i.e. worst-case comparisons h ≥ log₂(n!).

log(n!) is Θ(n log n)

  • Upper: n! = 1·2⋯n ≤ n·n⋯n = nn, so log(n!) ≤ n log n.
  • Lower: the top half of the factors, n/2 through n, are each ≥ n/2, and there are at least n/2 of them. So n! ≥ (n/2)n/2, giving log(n!) ≥ (n/2) log(n/2), which is Ω(n log n).
Example · small cases

n = 3: 3! = 6 orders, log₂ 6 ≈ 2.58, so some input needs 3 comparisons. n = 4: 24 orders, log₂ 24 ≈ 4.58, so 5 comparisons are needed in the worst case. n = 100: log₂(100!) ≈ 525.

Trap

The bound only covers comparison sorts. Counting and radix sort don’t compare items; they look at digits, so they can run in linear time. Also, the bound is about the worst case: insertion sort is Θ(n) on sorted input without contradicting it.

Someone claims a comparison sort that handles any 5 items with at most 6 comparisons. Possible?tap

No. 5! = 120 orders, and 2⁶ = 64 < 120 leaves. You need at least ⌈log₂ 120⌉ = 7 comparisons in the worst case.

14.6Counting sort

Big idea

If keys are small integers 0..R−1, don’t compare at all: count how many of each key there are, work out where each key’s block starts, then drop every item straight into its slot.

  1. Count occurrences of each key: Θ(N).
  2. Turn counts into starting positions (running sums): Θ(R).
  3. Scan the input left to right; put each item at its key’s next free position, then bump that position: Θ(N).
Example · keys 0..2 (R = 3), letters as tags 
input  2a 0b 2c 1d 0e 2f
counts key0=2 key1=1 key2=3
starts key0=0 key1=2 key2=3
output 0b 0e 1d 2a 2c 2f

The 2s come out a, c, f, the same order they went in: counting sort is stable because of the left-to-right scan in step 3.

Θ(N + R) time, Θ(N + R) spaceGreat when R is O(N). Terrible when R is huge (sorting 10 numbers that range up to 2³¹ needs a 2-billion-entry count array).

14.7LSD radix sort

Big idea

Sort by the last digit, then the second-to-last, …, finally the first, using a stable sort (counting sort) each time. Stability means ties on the current digit keep the order earned from the less significant digits.

Example · LSD radix sort of 253, 031, 512, 148, 023, 405, 330, 018 
input       253 031 512 148 023 405 330 018
ones digit  330 031 512 253 023 405 148 018
tens digit  405 512 018 023 330 031 148 253
hundreds    018 023 031 148 253 330 405 512
  1. Ones pass: keys 0,1,2,3,3,5,8,8. 253 stays before 023 (both 3) because it came first.
  2. Tens pass: keys 0,1,1,2,3,3,4,5. Among tens-digit 1, 512 comes before 018 because 2 < 8 was settled last pass.
  3. Hundreds pass: fully sorted.

Runtime

W passes (W = digits per key), each a counting sort Θ(N + R): Θ(W(N + R)). Pad shorter keys with leading zeros (numbers) or treat strings as left-aligned with a “blank” that sorts first.

Trap

Doing the passes in the wrong direction (most significant first) with LSD’s “sort the whole array each pass” approach gives a list sorted only by the last digit processed. And each pass must be stable, or earlier passes’ work is destroyed.

Ones digits: 1, 3, 2, 3, 1. Stable by ones digit: 41, 31, 42, 23, 13. (Then tens pass: 13, 23, 31, 41, 42.)

14.8MSD radix sort, and when radix wins

Big idea

Sort by the first character into buckets, then sort each bucket separately by the next character, and so on. Once a bucket has one item (or the keys are distinguished), stop.

Why separate subproblems? After sorting by the first letter, “bad” < “cab” is final. If you then re-sorted the whole array by second letter, “cab” (a) would jump ahead of “bed” (e), wrecking it. So MSD only refines within buckets.

Example · first pass of MSD on 12 three-letter words 
a: ace add        b: bad bed bee
c: cab            d: dab dad
e: ebb            f: fad fed fee

Buckets c and e are done. Bucket b recurses on the 2nd letter: bad | bed bee, then bed vs bee on the 3rd letter.

  • Best case Θ(N + R): the first character tells every key apart.
  • Worst case Θ(W(N + R)): all keys share long prefixes (e.g. all equal), so you go W levels deep.
  • Downside: lots of small subproblems, each paying Θ(R) for its count array. Real versions switch to insertion sort for small buckets.

Radix vs comparison sorts

Radix is not magic. For N keys of W characters, LSD is Θ(WN) (taking R as a constant), while mergesort does Θ(N log N) comparisons, each of which may cost up to Θ(W) for strings. Radix wins when keys are short and fixed-length (e.g. 32-bit ints as 4 bytes: 4 passes with R = 256) and N is large. Comparison sorts win for very long keys that differ early, or when you only have a compareTo.

Sort 1,000,000 32-bit ints using LSD radix with R = 256. How many passes, and roughly how much work?tap

32 bits / 8 bits per digit = 4 passes. Each is Θ(N + R) ≈ 1,000,000 + 256. Total ≈ 4 million steps, vs about N log₂ N ≈ 20 million comparisons for a comparison sort.

15.1Prefix-free codes

Big idea

Give frequent symbols short bit patterns and rare symbols long ones. To decode without separators, no codeword may be the beginning (prefix) of another.

A code maps each symbol to a bitstring. It is prefix-free if no codeword is a prefix of another. Then a decoder reading bits left to right knows the instant a codeword ends. Prefix-free codes are exactly the codes you can draw as a binary trie: 0 = go left, 1 = go right, symbols only at leaves.

Example · a = 0, b = 10, c = 110, d = 111

Decode 1100111100: read until a codeword completes.

  1. 110 → c
  2. 0 → a
  3. 111 → d
  4. 10 → b
  5. 0 → a. Message: cadba.
Trap

{a = 0, b = 01, c = 1} is not prefix-free (0 is a prefix of 01): 01 could be “b” or “ac”. Being prefix-free is about codewords, not about the message.

15.2Huffman coding

Big idea

Build the code trie from the bottom up: repeatedly glue together the two least frequent nodes. Rare symbols get merged early and end up deep (long codes); common symbols are merged last and stay near the root (short codes). This gives an optimal prefix-free code for the given frequencies.

  1. Make a leaf for each symbol, weighted by its frequency. Put them all in a min-PQ.
  2. Remove the two smallest, make a parent with weight = their sum (smaller one as the 0/left child), insert the parent.
  3. Repeat until one tree remains. Read codes from root-to-leaf paths.

merge F(3) + E(4)    -> 7
merge D(5) + C(6)    -> 11
merge FE(7) + B(10)  -> 17
merge DC(11) + 17    -> 28
merge A(20) + 28     -> 48 (root)

  • Building: Θ(R log R) with a heap for R symbols. Encoding a file of N symbols: Θ(N) with a lookup table. Decoding: walk the trie bit by bit, restarting at the root at each leaf.

15.3Limits of compression

Big idea

No lossless compressor can make every input shorter. There aren’t enough short bitstrings to go around.

Counting (pigeonhole) argument: there are 2⁸ = 256 bitstrings of length 8, but only 1 + 2 + 4 + ⋯ + 128 = 255 bitstrings of length less than 8. A lossless compressor must send different inputs to different outputs, so at least one 8-bit input can’t shrink. The same holds at every length. Compression only works because real data (text, images) is highly non-random: it repeats patterns.

  • Compressing an already-compressed file (or random noise) usually makes it slightly bigger.
  • Another view from lecture: a compressed file is really “a program plus data that regenerates the original”. The shortest such program measures how much real information the data has.
  • LZW (used in GIF and some zip-like tools) takes a different approach from Huffman: it builds a table of repeated substrings as it goes and outputs table indices, so it exploits repetition, not just letter frequencies.
A company claims its compressor shrinks every file by at least 1 bit. Why is that impossible?tap

Apply it to all 2ⁿ files of length n. Every output would have fewer than n bits, but there are only 2ⁿ − 1 such strings. Two inputs must share an output, so decompression can’t recover both. (And if it worked, you could apply it repeatedly to shrink anything to nothing.)

15.4Software engineering: complexity

Big idea

The main enemy in big programs isn’t slow code; it’s complexity: anything about a system’s structure that makes it hard to understand or change. It builds up gradually, one small shortcut at a time.

Three symptoms

  • Change amplification: a simple change needs edits in many places (e.g. a color hard-coded in 40 files).
  • Cognitive load: how much you must know or hold in your head to make a change safely.
  • Unknown unknowns: you can’t even tell what code you need to change or what you need to know. The worst symptom.

Two causes

  • Dependencies: code that can’t be understood or changed in isolation.
  • Obscurity: important information isn’t obvious (vague names, hidden assumptions, missing docs).

Tactical vs strategic programming

Tactical: get this feature working as fast as possible; each hack seems harmless, and complexity piles up (a “tactical tornado” leaves a mess for others). Strategic: working code isn’t enough; invest a little time continually in good design so future changes are cheap.

15.5Deep modules and information hiding

Big idea

A module’s interface is what users must know; its implementation is what it does for them. The best modules are deep: a small, simple interface hiding a lot of functionality.

  • Deep: a hash map. put, get, remove hide hashing, buckets, resizing, collision handling. Similarly a garbage collector has essentially no interface and does enormous work.
  • Shallow: the interface is almost as complicated as the implementation, so the module saves you nothing (e.g. a class whose methods each just forward to one line of another class, or a dozen tiny classes you must wire together to read a file).
  • Information hiding: each module encapsulates design decisions (data layout, algorithms) so others don’t depend on them. In Java: private fields, returning interfaces (List) not implementations. Information leakage is when one decision shows up in several modules, so changing it means changing all of them.

Lecture 38’s theme (AI in software engineering) fits the same frame: generated code still has to be understood, tested and kept simple; it is easy to produce complexity fast.

A teammate makes every field public “so other classes can use whatever they need”. Which complexity symptoms does this invite?tap

Change amplification (changing a field’s representation breaks every class that touches it) and unknown unknowns (you can’t tell who depends on the field). It removes information hiding, so the module becomes shallow: its whole implementation is its interface.
